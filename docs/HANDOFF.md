Состояние описано на **14 ноября 2026 года**. Если код и документ расходятся, прав код: обновите документ в том же коммите, где меняете поведение.

Как читать:

- **Новый человек в команде:** разделы 1, 2, 3 и 11, потом нужная задача из раздела 10.
- **ИИ-модель, получившая задачу:** сначала [AGENTS.md](../AGENTS.md) (короткие правила), затем разделы 4–8 по затрагиваемым модулям и раздел 9 (принципы игры). Не меняйте числа в каталоге, не прогнав тесты баланса (раздел 8).

## 1. Задание и цель игры

### Исходное задание (кратко)

Нужно сделать интерактивную игру, в которой участник проектирует **космическую миссию целиком**: формулирует цель, проектирует аппарат, выбирает приборы, ракету и орбиту, управляет ограничениями (бюджет, масса, энергия, связь, данные, срок работы) и видит, как каждое решение влияет на остальные части миссии.

Главная мысль задания: **в миссии всё связано, и идеального решения нет**. Более мощный прибор даёт больше науки, но добавляет массу, потребление, объём данных и цену.

Пожелания задания (обязательных пунктов нет, везде «may consider»):

| Пожелание | Где в игре |
| --- | --- |
| Начинать с цели миссии | Раздел «Задача» в конструкторе |
| Последствие у каждого решения | Таблицы компонентов и шкалы ресурсов |
| Несколько решений одной задачи | 2–3 орбиты на миссию, разные наборы приборов |
| Реальные ограничения | Шесть шкал в правой колонке конструктора |
| Компоненты аппарата | Корпус, энергия, батарея, связь, компьютер, ориентация, двигатель, приборы |
| Простые и продвинутые компоненты | Флаг `advanced` в каталоге, скрыт на уровне «Кадет» |
| Орбиты с объяснением | 8 орбит в `catalog.ts` с описаниями |
| Совместимость массы и орбиты с ракетой | Обязательные замечания `vehicle_reach`, `overweight` |
| Ресурсы всегда на виду | Шкалы `Budgets` в `Studio.tsx` |
| Объяснение причин успеха и провала | Замечания комиссии + «Почему так вышло» в разборе |
| Многократная симуляция | «Доработать проект», «Запустить ещё раз» |
| Очки за науку, экономию, решения | `report.ts` |
| Уровни сложности, сценарии | 3 уровня, 5 миссий + песочница |
| Случайные события | В полёте — да; на этапе разработки — нет (задача 10.5) |
| Командная игра с ролями | Сделано: до 3 человек, 4 роли (раздел 6) |
| Переговоры между ролями | Личные цели ролей + чат |
| Таблица лидеров | Локальная; общая — задача 10.9 |
| Сохранить, поделиться, сравнить | Сохранение и ссылка есть; сравнения нет (задача 10.7) |
| Песочница | Шестая «миссия» |
| Обучение простым языком | Абзац-урок в каждом разделе, описания компонентов |

### Аудитория и тон

Школьники старших классов, студенты, начинающие инженеры. Знаний о космосе не предполагается. Тон: спокойный, точный, без жаргона; если термин необходим, он объясняется в той же фразе.

### Решения, принятые владельцем проекта

- Язык общения в проекте — русский; игра двуязычная (русский по умолчанию, английский).
- Команда — **до трёх человек** (не четырёх). Ролей четыре, поэтому при трёх игроках один ведёт две.
- Репозиторий публичный: https://github.com/doniar4/mission-forge. Коллабораторов владелец добавляет сам.

## 2. Что уже сделано

### Этап 1 — одиночная игра (готово, проверено)

- Главная страница: заявки на миссии, уровень сложности, таблица лучших результатов, вход в командную игру.
- Конструктор из 7 разделов с таблицами компонентов, чертежом аппарата, шестью шкалами ресурсов и замечаниями комиссии.
- Симуляция полёта по месяцам с анимацией орбиты, графиком науки и бортовым журналом.
- Разбор миссии: оценка S–F, счёт из слагаемых, текстовый анализ причин.
- Сохранение черновиков в браузере, ссылка на проект, локальный лидерборд.

### Этап 2 — командная игра (готово, проверено в двух вкладках)

- Комнаты по 5-символьному коду или ссылке-приглашению, до 3 игроков.
- Два режима связи: «По интернету» (PeerJS/WebRTC) и «На этом компьютере» (BroadcastChannel между вкладками).
- Лобби: выбор миссии и сложности (хозяин), разбор ролей, автоматическая раздача свободных ролей, смена имени, чат.
- В конструкторе каждый меняет только разделы своих ролей, остальное видит в режиме чтения.
- Личные цели ролей (10 целей), которые тянут проект в разные стороны.
- Запуск только когда все владельцы ролей подтвердили проект; любое изменение снимает подтверждения.
- Одинаковый полёт и одинаковый счёт у всех игроков (общий seed), строка «Согласованность команды».

### Как это проверено

- 31 автоматический тест (`npm test`): физика, баланс эталонных проектов, правила командного судьи.
- `npm run build`: проверка типов и сборка проходят.
- В браузере вручную: одиночная миссия «Пожарный дозор» целиком; командная игра «хозяин + гость» в двух вкладках в локальном режиме: создание комнаты, вход, роли, права на разделы, чат, подтверждение, полёт, одинаковый счёт 735 у обоих, возврат к проектированию.
- **Не проверено:** режим «По интернету» между разными устройствами (нужны два реальных устройства), три игрока одновременно, экран аварии при запуске, миссии кроме «Пожарного дозора» в браузере (они покрыты только тестами), разные размеры экрана для командных экранов.

## 3. Запуск и инструменты

Требования: Node.js 20+ (проверено на 24), npm.

```bash
npm install
npm run dev        # dev-сервер Vite на http://localhost:5173
npm test           # vitest: тесты ядра (src/**/*.test.ts)
npm run build      # tsc --noEmit + vite build в dist/
npm run preview    # просмотр собранной версии
```

Стек:

| Что | Версия | Зачем |
| --- | --- | --- |
| Vite | 8 | сборка, dev-сервер; `base: './'` для GitHub Pages |
| React | 19 | интерфейс |
| TypeScript | 7, `strict`, `noUnusedLocals` | типы |
| zustand | 5 (+ `persist`) | состояние, сохранение в localStorage |
| peerjs | 1.5 | WebRTC для командной игры (подгружается лениво) |
| vitest | 5 | тесты |

Шрифты: Jost (заголовки) и Golos Text (текст) из Google Fonts, подключены в `index.html`. Других внешних ресурсов нет.

Для Claude Code в репозитории есть `.claude/launch.json` (конфигурация dev-сервера `mission-forge` на порту 5173).

## 4. Архитектура

### Слои

```
┌──────────────────────────────────────────────────────────────┐
│ ui/            React-экраны и компоненты (только отображение) │
├──────────────────────────────────────────────────────────────┤
│ store.ts       zustand: экран, проекты, результаты, команда   │
│ i18n.ts        переводчик t()                                │
├──────────────────────────────────────────────────────────────┤
│ team/net.ts    сессия комнаты: хозяин-судья, игроки           │
│ team/transport.ts  PeerJS и BroadcastChannel за одним API     │
├──────────────────────────────────────────────────────────────┤
│ engine/        ЧИСТЫЕ функции без React, DOM и сети           │
│   types → catalog → scenarios → design → evaluate             │
│                                   ↘ simulate → report         │
│   team (судья команды, цели ролей)                            │
└──────────────────────────────────────────────────────────────┘
```

Правило зависимостей: `engine/` не импортирует ничего за пределами `engine/`. `store.ts` не импортирует `team/net.ts` (иначе цикл); сеть подключается через `setTeamHooks()`.

### Поток данных в одиночной игре

```
клик по компоненту → store.patch(p) → designs[scenarioId] обновлён
  → Studio: evaluate(design, sc, diff) (useMemo) → шкалы, замечания
  → «Запустить миссию» → store.launch() → simulate(design, sc, diff, seed) → sim
  → Flight проигрывает sim.months → Debrief: buildReport(...)
```

### Поток данных в командной игре

```
игрок кликает → store.patch(p) → hooks.patch → teamSend({t:'patch', patch})
  → у гостя: сообщение уходит хозяину по транспорту
  → у хозяина: reduce(state, from, msg, {seed}) → новый TeamState (rev+1)
  → хозяин рассылает {t:'state', state} всем и применяет у себя
  → apply(state) у каждого: store.team.state = state; дизайн берётся из state.design
  → когда state.phase === 'flight': каждый сам считает simulate(..., state.seed)
```

Полёт по сети не передаётся: передаётся только seed, а симуляция детерминирована. Поэтому `simulate` **нельзя** делать зависимым от времени, `Math.random` или порядка ключей объектов.

### Структура файлов

```
src/
  main.tsx              точка входа: читает ссылки (#m=..., #room=...), монтирует App
  App.tsx               маршрутизация по store.screen, тема (paper/space)
  store.ts              состояние игры, сохранение, ссылки на проект
  i18n.ts               useT(), makeT()
  styles.css            все стили, токены цвета в :root
  engine/
    types.ts            все типы данных
    catalog.ts          орбиты, приборы, компоненты, ракеты, испытания, сложность
    scenarios.ts        миссии, emptyDesign()
    design.ts           sanitize(): приводит проект к допустимому виду
    evaluate.ts         бюджеты и замечания комиссии
    simulate.ts         полёт по месяцам
    report.ts           счёт и объяснения
    team.ts             судья командной игры, цели ролей
    engine.test.ts      тесты физики и баланса

    net.ts              создание комнаты, вход, рассылка состояния
  ui/
    Home.tsx            главная

    Studio.tsx          конструктор (рамка, шкалы, замечания)

    ScienceChart.tsx    график науки

    common.tsx          роли, переключатель языка, шапка, шкала Gauge, глифы
docs/
```

## 5. Расчётное ядро: модули и функции

Все числа упрощены, но сохраняют реальные пропорции. Единицы: масса — кг, мощность — Вт, деньги — млн долларов, данные — ГБ в сутки, скорость связи — Мбит/с, изменение скорости — м/с.

### 5.1 `engine/types.ts` — типы

| Тип | Что это |
| --- | --- |
| `L` | `{ ru: string; en: string }` — **любой** текст для игрока хранится так |

| `Orbit` | орбита (поля ниже) |
| `Part` и наследники | `Instrument, PowerSource, Battery, Antenna, Computer, Adcs, Propulsion` |

| `adcs` | id ориентации | engineer | `'magnetic'` |

### 5.2 `engine/catalog.ts` — каталог

Экспорт: `MEASURES`, `ORBITS`, `INSTRUMENTS`, `POWER`, `BATTERIES`, `ANTENNAS`, `GROUNDS`, `COMPUTERS`, `ADCS`, `PROPULSION`, `STRUCTURES`, `VEHICLES`, `TESTING`, `DIFFICULTY`, функции `byId(list, id)` (элемент или `undefined`) и `pick(list, id)` (элемент или первый, самый простой — чтобы устаревший проект не ломал игру).

Поля орбиты `Orbit`:

| Поле | Смысл |
| --- | --- |
| `capFactor` | доля грузоподъёмности ракеты на низкую орбиту, которая доходит сюда |
| `insertionDv` | м/с, которые аппарат должен обеспечить сам (торможение у Луны/Марса, подъём на ГСО) |
| `stationDv` | м/с в год на удержание орбиты |
| `disposalDv` | м/с на увод с орбиты в конце (только SSO, GEO) |
| `decayYears` | через сколько лет орбита разрушится без двигателя (`null` — стабильна) |
| `sunFraction`, `eclipseHours` | доля времени на свету, самая длинная тень |
| `solarFactor` | яркость Солнца относительно Земли (Марс 0,43) |
| `radiation` | 1–3 |
| `commsFactor` | множитель скорости связи (сжат для играбельности) |
| `contact` | часы связи в сутки для каждой наземной станции |
| `transitMonths`, `lowThrustMonths` | перелёт; добавка при ионном двигателе |
| `magnetic` | есть ли магнитное поле для магнитных катушек |
| `heaterW` | обогрев, Вт |
| `opsPerYear` | стоимость команды управления, млн $/год |

Орбиты и их назначение:

| id | Тело | Особенность |
| --- | --- | --- |
| `leo` | Земля | дёшево, распад за 4 года без двигателя, полюса не видны |
| `sso` | Земля | идеальна для съёмки, нужен увод (120 м/с) |
| `geo` | Земля | постоянный обзор полушария, 40% груза, 1500 м/с |
| `llo` | Луна | лучшее разрешение, 150 м/с/год на удержание |
| `elo` | Луна | дешевле, но дальше от поверхности |
| `l1` | Солнце | без тени, солнечный ветер за час до Земли |
| `lmo` | Марс | 2200 м/с торможения |
| `emo` | Марс | 1100 м/с, меньше деталей |

Приборы `Instrument`: `mass, power, cost, data (ГБ/сут), measures (качество 0..1 по видам измерений), pointing (нужное наведение 1–3), devMonths, advanced?`. Всего 12; SAR (радар) — продвинутый.

Уровни сложности `DIFFICULTY`:

| | budget | events | launchFailures | advanced | scoreFactor |
| --- | --- | --- | --- | --- | --- |
| cadet | ×1,25 | ×0,4 | нет | нет | ×0,85 |
| engineer | ×1 | ×1 | да | да | ×1 |
| director | ×0,88 | ×1,5 | да | да | ×1,15 |

Названия ракет вымышленные («Колибри», «Вектор», «Атлант», «Титан-Икс», «Попутный запуск»). Реальные бренды не использовать.

**Как добавить компонент:** добавьте объект в нужный массив с уникальным `id`, двуязычными `name` и `desc`; если он сложный — `advanced: true`; прогоните `npm test`. Если эталонные проекты перестали проходить, вы изменили баланс — разберитесь до коммита.

### 5.3 `engine/scenarios.ts` — миссии

| Экспорт | Сигнатура | Что делает |
| --- | --- | --- |
| `SCENARIOS` | `Scenario[]` | 5 миссий + песочница |
| `scenarioById` | `(id: string) => Scenario` | миссия или первая, если id неизвестен |
| `scenarioOrbits` | `(sc) => OrbitId[]` | орбиты, допустимые в миссии |
| `emptyDesign` | `(sc) => Design` | стартовый проект |

Поля `Scenario`: `id, body, stars, name, tagline, brief (все L), budget (на уровне engineer), deadlineMonths, targetYears, weights (вес каждого измерения, сумма 1), orbits ({ [orbitId]: { fit 0..1, note: L } }), sandbox?`.

| id | Бюджет | Срок | Лет | Главные измерения |

### 5.5 `engine/evaluate.ts` — бюджеты и комиссия

Константы: `BUS_BASE_KG = 15`, `BUS_BASE_W = 20` (служебные системы), `TANK = 0.1` (баки — 10% массы топлива), `DOD = 0.7` (безопасно расходуемая доля батареи), `TARGET_QUALITY = 0.75`, резервирование: масса платформы ×1,15, цена ×1,25.

| Функция | Сигнатура | Что делает |
| --- | --- | --- |
| `resolve` | `(d) => Resolved` | превращает id в объекты каталога (`orbit` может быть `null`, `veh` может быть `null`) |
| `scienceQuality` | `(insts, pointing, sc) => { quality, total }` | качество каждого измерения; два прибора на одно измерение — убывающая отдача: `1 − Π(1 − q·устойчивость)`; если наведение хуже нужного, качество × `0,45^(разница)` |
| `performance` | `(r: Flying, sc, s: FlightState) => {...}` | снимок работы аппарата: энергия, данные, наука в секунду времени; используется и в оценке, и каждый месяц симуляции |
| `propellantFor` | `(dryKg, dv, isp) => number` | формула Циолковского с баками: `k = e^(dv/(isp·g0)) − 1`, топливо `= dry·k / (1 − TANK·k)`; если знаменатель ≤ 0,02 — `Infinity` (манёвр невозможен) |
| `evaluate` | `(d, sc, diff) => Evaluation` | полная оценка проекта + замечания |
| `clamp` | `(x, lo=0, hi=1)` | ограничение |
| `fmt` | `(x) => string` | короткое число для текстов ядра |

Формулы внутри `performance`:

- Нагрузка служебных систем: `20 + компьютер + антенна + ориентация + обогрев орбиты`.
- Старение: солнечные панели теряют `2% + 1%·(радиация − 1)` в год, РИТЭГ — 1,5%.
- Средняя выработка солнечных панелей: `watts · solarFactor · sunFraction · arrayFactor · старение`.
- Служебные системы питаются первыми; приборам достаётся остаток: `instFrac = clamp((выработка − служебные) / приборы)`.
- В тени работа держится на батарее: `батарея = wh · 0,7 · 0,96^лет`; если её не хватает, приборы спят часть тени.
- Данные: `сгенерировано = Σ data · сжатие компьютера · duty`; скорость `= mbps · commsFactor · gain станции · штраф наведения антенны`; передано за сутки `= скорость · часы связи · 0,45 · availability` (0,45 переводит Мбит/с·ч в ГБ); память нужна `сгенерировано · (1 − часы/24) · 1,5`.

Формулы внутри `evaluate`:

- Масса: приборы + платформа + корпус (`fraction · (приборы + платформа)`) + топливо + баки. Запас массы `(capacity − wet) / capacity`, где `capacity = leoKg ракеты · capFactor орбиты`.
- Δv: выход на орбиту + удержание × годы (только с двигателем) + увод.
- Время разработки, мес.: `round(14 + 0,7·max(devMonths приборов) + 1,5·число приборов + испытания + доп. месяцы РИТЭГа/лазера/ионного двигателя + подготовка ракеты + 3 при резервировании)`.
- Стоимость: приборы + платформа + корпус + ракета + наземные станции (`setup + yearly·годы полёта`) + команда управления (`opsPerYear·(годы + перелёт/24)`) + разработка (`месяцы · (0,6 + сухая масса/500)`) + испытания.
- Цель науки: `targetYears · 100 · 0,75`. Прогноз: `ratePerYear · duty · returnFraction · effectiveYears / цель`.

Замечания комиссии (`Check.id`): **blocker** запрещают запуск, **warn** разрешают, но последствия проявятся в полёте.

### 5.6 `engine/simulate.ts` — полёт

| Функция | Сигнатура | Что делает |
| --- | --- | --- |
| `mulberry32` | `(seed) => () => number` | детерминированный генератор случайных чисел |
| `simulate` | `(d, sc, diff, seed) => SimResult` | полёт по месяцам; вызывать только для проекта без blocker-замечаний (иначе бросает ошибку при отсутствии орбиты или ракеты) |

Порядок событий:

1. **Запуск.** Если у сложности `launchFailures`, авария с вероятностью `1 − reliability` ракеты.
2. **Перелёт.** `transitMonths` месяцев без науки.
3. **Каждый месяц работы:**
   - распад орбиты (без двигателя после `decayYears`) — потеря;
   - в первый месяц при минимальных испытаниях — скрытый дефект с вероятностью `6% · events`;
   - солнечная буря с вероятностью `1,2% · радиация · events`; если электроника не рассчитана на радиацию — безопасный режим или потеря прибора (`20% · дефицит стойкости`);
   - случайный отказ с вероятностью `0,4% · failFactor испытаний · (0,35 при резерве) · events · (1 + 0,15·годы)`; тип отказа: прибор (30%), маховик (20%), секция панелей −20% (20%), передатчик ×0,5 (18%), бортовой компьютер (12%: при резерве один раз спасает, иначе потеря);
   - простой наземной станции с вероятностью `2% · events` (−30% сеансов);
   - потеря питания, если выработка ниже 85% служебной нагрузки;
   - гибель батареи от глубоких разрядов, если она покрывает меньше 40% тени (4% в месяц);
   - наука за месяц: `ratePerYear / 12 · duty · returnFraction` (0 в безопасном режиме).

Итог: `sciencePct = наука / цель`; `outcome`: `success` при ≥ 1, `partial` при ≥ 0,5, иначе `failure`.

**Детерминизм обязателен:** один и тот же `(design, scenario, difficulty, seed)` всегда даёт тот же `SimResult` (на этом держится командная игра; тест `the same seed replays the same mission`). Любые новые случайности — только через `rng()`, в фиксированном порядке вызовов.

### 5.7 `engine/report.ts` — счёт и объяснения

`buildReport(d, sc, diff, ev, sim, team?: { met, total }): Report`

| Строка | Максимум | Как считается |
| --- | --- | --- |
| Научный результат | 500 | 80% за достижение цели; оставшиеся 20% за перевыполнение до 140% |
| Экономия бюджета | 175 | запас бюджета / 30% |
| Доставка данных | 75 | переданные / созданные |
| Живучесть аппарата | 75 | отработанные / плановые месяцы |
| Инженерные запасы | 75 | среднее из (запас массы / 10%) и (запас энергии / 15%) |
| Соблюдение сроков | 50 | `1 − (разработка − срок) / 12` |
| Чистота космоса | 50 | увод с орбиты возможен |
| Согласованность команды | 100 | только в командной игре: выполненные цели ролей / все цели |

Итог нормируется к шкале 0–1000 (`raw / maxRaw · 1000`) и умножается на `scoreFactor` сложности. Оценки: S ≥ 920, A ≥ 820, B ≥ 700, C ≥ 550, D ≥ 400, иначе F.

`insights` — список объяснений «почему так вышло» (энергобаланс, данные, топливо, орбита, приборы, бюджет, сроки, мусор, цели команды). Каждое объяснение говорит **причину и что с ней можно сделать**, а не «правильно/неправильно».

## 6. Командная игра: протокол и сеть

### Модель

Звезда: хозяин — судья и единственный владелец истинного `TeamState`. Игроки шлют **намерения** (`ClientMsg`), хозяин применяет `reduce` и рассылает **всё состояние целиком** (`{ t: 'state', state }`). Состояние маленькое (единицы килобайт), поэтому дельты не нужны.

### `team/transport.ts`

| Экспорт | Что делает |
| --- | --- |
| `hostRoom(code, kind, { onMessage(from, m), onLeave(from) })` → `HostLink { broadcast, sendTo, close }` | открыть комнату |
| `joinRoom(code, kind, { onMessage(m), onClose() })` → `{ link: ClientLink { send, close }, myId }` | войти |
| `RoomError(code: 'taken' \| 'notfound' \| 'network')` | ошибки |

Режим `local` (BroadcastChannel `mission-forge-room-<CODE>`): кадры `probe/here` (код занят?), `hello/welcome` (вход, ждём 3 с), `msg {from, body}` (игрок → хозяин), `all {body}` / `to {to, body}` (хозяин → игроки), `bye {from}` (уход, также на `pagehide`).

Режим `online` (PeerJS): хозяин регистрирует peer id `mission-forge-<CODE>` на бесплатном брокере PeerJS (`0.peerjs.com`); игрок создаёт случайный peer и подключается к нему. Брокер видит только id и код комнаты; проект и чат идут напрямую между браузерами через WebRTC. TURN-сервер **не настроен**: при строгом NAT (некоторые школьные сети) соединение не установится — задача 10.3.

### `team/net.ts`

| Экспорт | Что делает |
| --- | --- |
| `createTeam({ kind, name, scenarioId, difficulty })` | до 5 попыток подобрать свободный код, создать комнату, перейти в лобби |
| `joinTeam(code, kind, name)` | войти; если за 6 с не пришло состояние — «Хозяин комнаты не ответил» |
| `leaveRoom()` | закрыть соединения, сбросить `store.team` |
| `teamSend(msg)` | единая точка «я сделал действие»: у хозяина — сразу `reduce`, у игрока — отправка хозяину |
| `readRoomLink()` | открыть приглашение `#room=CODE&k=online\|local` из адресной строки |
| `roomLink(code, kind)`, `normalizeCode(s)` | ссылка-приглашение, нормализация кода |
| `useNet` | zustand: `{ busy, error }` для кнопок на главной |

`apply(state)` (внутренняя) синхронизирует экран с фазой: `lobby` → лобби, `design` → конструктор, `flight` → считает `simulate` с `state.seed` (один раз на пару `code:seed`) и открывает полёт.

Ошибки показываются игроку по-русски и по-английски (`E` в `net.ts`): код занят, комната не найдена, нет связи с PeerJS, комната заполнена, хозяин закрыл комнату, связь потеряна.

### Ограничения, о которых нужно помнить

- Хозяин закрыл вкладку — комната исчезла. Перенос роли хозяина не реализован.
- Перезагрузка страницы выкидывает из комнаты (состояние комнаты не сохраняется).
- Кнопка «Доработать проект» у любого игрока возвращает в конструктор **всех**, даже тех, кто ещё читает разбор.
- Чат не модерируется: при игре со школьниками это нужно учитывать (задача 10.10).
- Хозяин доверяет id отправителя из транспорта; в локальном режиме id приходит в самом сообщении, поэтому сообщения с `from === 'host'` отбрасываются.

## 9. Что учитывать в игре: принципы и запреты

### Принципы геймдизайна

1. **У каждого решения есть цена.** Новый компонент или параметр должен влиять минимум на два ресурса. Компонент, который только улучшает, — ошибка дизайна.
2. **Нет единственного правильного ответа.** Каждая миссия должна решаться минимум двумя разными способами (другая орбита, другой набор приборов, дольше работать).
3. **Объяснять причину, а не выносить вердикт.** Каждое замечание и каждое объяснение отвечает: что произошло, почему (с числами игрока) и что можно поменять. Плохо: «Ошибка энергии». Хорошо: «Нужно 160 Вт, в среднем есть 120: приборы будут работать 60% времени».
4. **Понятия вводятся через игру.** Термин впервые появляется там, где он нужен для решения, и объясняется в той же фразе.
5. **Предупреждение не запрещает полёт.** Блокер — только физически невозможное или неутверждаемое (нет ракеты, перевес, нет денег). Всё остальное — риск, последствия которого игрок увидит в полёте.
6. **Командные цели должны конфликтовать.** Если все цели ролей выполняются одним очевидным проектом, переговоров не будет.
7. **Числа упрощены, пропорции настоящие.** Не придумывайте эффектов, которых нет в реальности. Сознательные упрощения (сжатая зависимость связи от расстояния) описывайте в README.

### Технические правила

- `engine/` — чистые функции: без React, DOM, `Date.now()`, `Math.random()` (кроме `rng()` в симуляции), без сети.
- Детерминизм `simulate` обязателен.
- Любой проект извне — через `sanitize`.
- Любая строка для игрока — на двух языках (`L` или `t(ru, en)`).
- Новые замечания: добавить в `evaluate.ts`, в `WHERE` в `Studio.tsx`, при необходимости в `goalsFor`.
- Новое поле `Design`: тип, `emptyDesign`, `sanitize`, `ROLE_FIELDS` (какой роли принадлежит), UI раздела, тесты.
- Доступность: видимый фокус, подписи у полей, `aria-*` у переключателей, контраст, `prefers-reduced-motion`, ширина от 375 px без горизонтальной прокрутки.

### Запреты

- Не использовать логотипы, названия и стиль реальных организаций и компаний (NASA, SpaceX и т. п.) как будто игра от их имени. Ракеты и сервисы — вымышленные.
- Не класть секретные ключи (API Claude и др.) в код фронтенда — сайт статический и публичный.
- Не отправлять имена игроков и чат во внешние сервисы (включая ИИ-наставника).
- Не коммитить `dist/` и `node_modules/`.

## 10. Что делать дальше: задачи с критериями готовности

Порядок — по приоритету. Каждая задача — отдельная ветка и отдельный PR.

### 10.1 [P0] Публикация на GitHub Pages и CI

**Зачем:** игра должна открываться по ссылке без установки — это нужно и для командной игры по сети.

Шаги:
1. `.github/workflows/ci.yml`: на каждый push и PR — `npm ci`, `npm test`, `npm run build`.
2. `.github/workflows/pages.yml`: на push в `main` — сборка и публикация `dist/` через `actions/upload-pages-artifact` и `actions/deploy-pages`.
3. Владелец включает Pages в настройках репозитория (Source: GitHub Actions).
4. Ссылку на игру добавить в README.

Готово, когда: ссылка вида `https://doniar4.github.io/mission-forge/` открывает игру, приглашения `#room=...` работают с неё, CI зелёный.

Учесть: `base: './'` уже стоит в `vite.config.ts`; ссылки-приглашения строятся из `location.pathname`, поэтому подпуть репозитория поддерживается.

### 10.2 [P0] Проверка командной игры на реальных устройствах

Шаги: после 10.1 сыграть втроём с трёх устройств в режиме «По интернету»; проверить вход по ссылке, вход по коду, уход игрока, закрытие вкладки хозяина, телефонную ширину лобби и командной панели. Найденное — в issues.

Готово, когда: полный цикл (лобби → проект → подтверждения → полёт → разбор) прошёл на трёх устройствах; ошибки описаны или исправлены.

### 10.3 [P1] Надёжность сети

- TURN-сервер для строгих NAT (настройка `config.iceServers` при создании `Peer`); бесплатных надёжных TURN почти нет — решение за владельцем проекта.
- Переподключение игрока после короткого обрыва с тем же местом и ролями (сейчас обрыв = выход).
- Передача роли хозяина или явное «комната закрыта» с сохранением проекта у всех (кнопка «Сохранить проект себе»).
- Не выдёргивать игроков из разбора по `back`: показывать «Команда вернулась к проекту» с кнопкой перехода.

### 10.4 [P1] ИИ-наставник внутри игры

**Зачем:** игроку без подготовки нужна подсказка «в какую сторону думать», а не готовый ответ. Сейчас подсказки — только детерминированные замечания комиссии; наставник добавляет объяснение своими словами и наводящие вопросы.

**Где в игре:**
- кнопка «Спросить наставника» в правой колонке конструктора (под замечаниями);
- блок «Разбор от наставника» на экране разбора (необязательный, по кнопке);
- в командной игре — подсказка для своей роли с учётом целей ролей.

**Архитектура** (сайт статический, поэтому нужен небольшой сервер-посредник):

```
браузер ──POST /api/tutor──▶ serverless-функция ──▶ Claude API
                               (ключ ANTHROPIC_API_KEY
                                только здесь, в секретах)
```

Варианты размещения функции: Vercel Functions или Cloudflare Workers. Решение — за владельцем (у Vercel есть готовый плагин в окружении разработки). GitHub Pages функций не выполняет: при выборе Vercel можно перенести туда и сам сайт.

**Контракт запроса:**

```ts
// POST /api/tutor
interface TutorRequest {
  lang: 'ru' | 'en';
  scenarioId: string;
  difficulty: 'cadet' | 'engineer' | 'director';
  role?: 'manager' | 'science' | 'engineer' | 'comms'; // в командной игре
  mode: 'hint' | 'debrief';
  design: Design;                 // после sanitize
  summary: {                      // сжатая Evaluation, только числа
    massKg: number; massCapKg: number;
    powerLoadW: number; powerAvgW: number;
    dataGenGB: number; dataDownGB: number;
    costM: number; budgetM: number;
    devMonths: number; deadlineMonths: number;
    sciencePct: number;
    checks: { id: string; level: 'blocker' | 'warn' }[];
    goals?: { id: string; role: string; met: boolean }[];
  };
  sim?: { outcome: string; sciencePct: number; lostCause?: string; monthsOperated: number; plannedMonths: number };
  question?: string;              // вопрос игрока, до 300 символов
}

interface TutorResponse {
  hint: string;          // 1–3 предложения, наводящие, без готового решения
  section: 'orbit' | 'payload' | 'power' | 'platform' | 'comms' | 'plan' | 'brief';
  concept: string;       // название понятия: «энергобаланс», «формула Циолковского»…
  question: string;      // наводящий вопрос игроку
}
```

**Вызов Claude** (TypeScript, официальный SDK `@anthropic-ai/sdk`, никаких самописных fetch-обёрток):

- Модель по умолчанию: `claude-opus-5-5` с `output_config.effort: "low"` (подсказки короткие; у этой модели мышление всегда включено и управляется только `effort`, по умолчанию `medium`). Дешевле — `claude-sonnet-5-5` ($2/$10 за 1 млн токенов) или `claude-haiku-5-5` ($0,10/$0,50); у `claude-opus-5-5` — $4/$20. Переходить на более дешёвую модель — **решение владельца проекта** после сравнения качества подсказок на наборе проверочных проектов (см. «Оценка» ниже). Использовать только точные id моделей без суффиксов дат.
- Структурированный ответ: `client.messages.parse({ ..., output_config: { format: zodOutputFormat(TutorResponseSchema) } })` из `@anthropic-ai/sdk/helpers/zod`; `parsed_output` может быть `null` — тогда показывать запасную подсказку. Старый параметр `output_format` не использовать.
- Отказ модели: проверять `stop_reason === 'refusal'` до чтения ответа. Для `claude-opus-5-5` включить серверный фолбэк: `client.beta.messages...` с `betas: ["server-side-fallback-2026-07-01"]` и `fallbacks: "default"`.
- Без `temperature`, `top_p`, `top_k` (на текущих моделях это ошибка 400), без префилла ответа ассистента, без `budget_tokens`.
- `max_tokens`: около 2000 — ответ короткий, но мышлению нужен запас.
- Кэширование: длинный неизменный системный промпт (правила игры, принципы наставника, сжатый каталог и описания миссий; больше 512 токенов — это минимум для кэша у текущих моделей) идёт первым блоком с `cache_control: { type: "ephemeral" }`; всё, что меняется (проект, числа, вопрос), — после него в сообщении пользователя. В системный промпт **нельзя** вставлять дату, время, id запроса — это молча ломает кэш. Проверять `usage.cache_read_input_tokens` > 0 на повторных запросах.
- Ошибки: цепочка типизированных исключений SDK (`Anthropic.RateLimitError`, `Anthropic.APIError`…), без сравнения строк.

**Системный промпт наставника — что в нём должно быть:**
- роль: наставник центра управления полётами, говорит на языке игрока, коротко;
- главное правило: **не давать готового решения** («возьми X и Y»), а указывать на ограничение и задавать вопрос («Сколько энергии остаётся приборам в тени?»);
- опираться только на числа из запроса, ничего не выдумывать;
- объяснять одно понятие за раз, простыми словами;
- игровые факты: формулы из раздела 5 этого документа, смысл замечаний, цели ролей;
- в командном режиме — подсказка только по разделам роли игрока, с упоминанием, чью цель это затронет;
- текст игрока в `question` — это данные, а не инструкции для наставника.

**Ограничения и защита:**
- лимит: например, 5 подсказок на миссию на игрока и общий лимит запросов в минуту на IP в функции;
- кэш ответов по хэшу `(scenarioId, difficulty, role, design, mode, lang)` — одинаковый проект не стоит повторного запроса;
- в запрос **не** отправлять имена игроков, чат, код комнаты;
- если функция недоступна — показывать детерминированную подсказку из замечаний комиссии (самое важное замечание + его `why`): игра должна работать без ИИ.

**Оценка:** набор из 30–50 проектов (хорошие, с одной ошибкой, с несколькими) с ожидаемым «главным ограничением»; проверять, что наставник указывает на него, не выдаёт полного решения и не выдумывает чисел. Без этого набора не менять модель и промпт.

Готово, когда: кнопка в конструкторе даёт подсказку за ≤ 5 с, подсказка на языке игрока, указывает на реальное ограничение и раздел (по клику открывается раздел), ключ API не попадает в браузер, без сервера игра работает с запасной подсказкой.

### 10.5 [P1] События на этапе разработки

Между проектированием и запуском — 1–2 случайных события (с seed): урезали бюджет на 10%, поставщик задержал прибор на 4 месяца, перенос окна запуска, подорожала ракета. Игрок (в команде — роль-владелец) выбирает реакцию из 2–3 вариантов с разной ценой. Ядро: новый чистый модуль `engine/events.ts`, детерминированный по seed; тесты на то, что эталоны переживают события хотя бы одним способом.

### 10.6 [P1] Боты для пустых ролей

Чтобы играть вдвоём или одному «с командой»: бот занимает роль, предлагает изменения в чат по своим целям («Мне не хватает 40 Вт — можно взять средние панели?») и подтверждает запуск, когда его цели выполнены или явно отклонены. Первая версия — правила на основе `goalsFor` и замечаний, без ИИ; позже можно подключить наставника из 10.4.

### 10.7 [P2] Сравнение проектов

Кнопка «Сравнить с прошлой попыткой» в разборе: две колонки (проект, ресурсы, счёт), подсветка изменённых решений и того, как каждое повлияло на строки счёта.

### 10.8 [P2] Обучение

- Обучающая первая миссия с пошаговыми подсказками (поверх `firewatch` на уровне «Кадет»).
- Словарь терминов с короткими схемами: Δv, удельный импульс, энергобаланс, бюджет канала связи, солнечно-синхронная орбита. Термины в тексте — ссылки на словарь.

### 10.9 [P2] Соревнование команд и общий лидерборд

Режим «одна задача для нескольких команд»: одинаковая миссия и сложность, общий seed полёта, таблица команд. Нужен сервер с базой данных (общая таблица результатов, защита от подделки счёта: сервер сам пересчитывает `evaluate` и `simulate` по присланному проекту и seed — ядро для этого уже чистое и детерминированное).

### 10.10 [P2] Безопасность для школ

Фильтр нецензурной лексики в чате и именах, кнопка «Скрыть сообщения игрока», ограничение длины. Только на клиенте у получателя (сервер не нужен).

### 10.11 [P2] Тесты интерфейса

Playwright: одиночный цикл миссии; командная игра в двух контекстах браузера в режиме `local`; проверка ширины 375 px без горизонтальной прокрутки; переключение языка.

### 10.12 [P3] Прочее

Больше миссий (телескоп, группировка спутников, посадочный аппарат); решения во время полёта (что отключить при нехватке энергии, продлевать ли миссию); экспорт отчёта о миссии в PDF; звук по желанию игрока.

## 12. Как работать в репозитории

- Ветка `main` — рабочая версия. Новая работа — в ветке `feature/<коротко>` или `fix/<коротко>`, затем PR.
- Перед PR: `npm test` и `npm run build` без ошибок; изменения интерфейса проверены на ширине 375 и 1440 px и на обоих языках.
- Сообщения коммитов — на английском, в повелительном наклонении («Add tutor endpoint»), с телом, объясняющим «зачем».
- Меняете поведение — обновите этот документ (`docs/HANDOFF.md`) и при необходимости `README.md` в том же PR.
- Числа баланса меняются только вместе с выводом строки баланса из тестов в описании PR.
- Код и комментарии — на английском; тексты игры — на русском и английском.
